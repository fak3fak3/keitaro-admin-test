# Указания для работы над проектом

Обязательны для людей и ИИ-агентов (Claude Code, Cursor, Windsurf и т.д.).

## 0. Порядок работы

**В начале сессии** прочитай:

1. [docs/PLAN.md](docs/PLAN.md): сделанные задачи, текущая задача, следующие шаги, открытые вопросы;
2. [docs/DECISIONS.md](docs/DECISIONS.md): принятые решения. Не пересматривай их без явной просьбы;
3. `git log --oneline -20` и `git status`: что уже сделано и что в работе.

**В конце каждого шага:**

1. весь набор тестов зелёный (`pytest`);
2. отметь выполненный шаг из `docs/PLAN.md` галочкой, обнови открытые вопросы;
3. если принято новое решение, допиши его в `docs/DECISIONS.md` с причиной;

Агент не заливает изменения в git, только пользователь.


## 1. TDD

Код пишется только через цикл **Red → Green → Refactor**:

1. **Red.** Сначала напиши тест на новое поведение. Запусти и убедись, что он падает,
   причём по правильной причине (не из-за опечатки или импорта).
2. **Green.** Напиши минимальный код, при котором тест проходит. Ничего сверх этого.
3. **Refactor.** Улучши код и тесты при зелёном прогоне. Поведение не меняется.

Правила:

- Нет продакшн-кода без падающего теста, который его требует.
- Один цикл = одно маленькое поведение. Не пиши пачку тестов наперёд.
- Баг-фикс начинается с теста, который воспроизводит баг.
- Перед тем как считать шаг завершённым, весь набор тестов зелёный: `pytest`.
- Внешний мир в юнит-тестах не трогаем:
  - Keitaro API мокаем через `respx`;
  - БД в тестах: SQLite in-memory (`sqlite+aiosqlite:///:memory:`);
  - зависимости FastAPI подменяем через `app.dependency_overrides`.
- Тесты описывают поведение, а не реализацию: проверяем результат и запросы к Keitaro,
  а не внутренние вызовы.
- Инструменты: `pytest`, `pytest-asyncio`, `httpx.AsyncClient` (тесты эндпоинтов), `respx`.
