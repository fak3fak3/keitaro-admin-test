# Принятые решения

Журнал решений: только дописывается. Если решение пересмотрено, добавь новую запись
«Заменяет №N», а старую пометь «Заменено №M», но не удаляй.

Формат записи: номер, заголовок, решение, почему.

## 1. Стек: FastAPI + SQLAlchemy 2.0 (async, ORM) + Alembic

- **Решение:** ORM в стиле 2.0 (`Mapped`, `mapped_column`, `select()`), `AsyncSession`, миграции через Alembic.
- **Почему:** требование вакансии; стиль 1.x (`Column`, `session.query`) устарел.

## 2. Тонкий бэкенд-прокси между фронтом и Keitaro

- **Решение:** фронт ходит только в наше API, бэкенд ходит в Keitaro.
- **Почему:** API-ключ не должен попадать в браузер; CORS; сценарии из нескольких запросов держим на сервере.

## 3. Свой клиент Keitaro на `httpx.AsyncClient`

- **Решение:** не используем сторонние SDK.
- **Почему:** официального Python SDK нет; keitaropy синхронный, aiokeitaro заброшен.

## 4. Слои: `api → services → repositories / clients → db`

- **Решение:** `api/` (роутеры), `services/` (логика), `schemas/` (Pydantic), `models/` (SQLAlchemy),
  `repositories/`, `db/`, `clients/keitaro/`, `core/config.py`.
- **Почему:** аналог Go-структуры handlers/services/domain/repos/db; сервисы не зависят от FastAPI и тестируются отдельно.

## 5. Pydantic-схемы отдельно от ORM-моделей

- **Решение:** `schemas/` и `models/` не смешиваются.
- **Почему:** ORM-объекты завязаны на сессию и ленивые загрузки; DTO и таблицы меняются по разным причинам.

## 6. Модели Keitaro отдельно от наших

- **Решение:** ответы Keitaro описаны в `clients/keitaro/schemas.py`.
- **Почему:** изменения их API не расползаются по нашему коду.

## 7. Что хранится в БД

- **Решение:** реестр созданных кампаний, журнал изменений офферов, кэш справочников.
- **Почему:** Keitaro остаётся источником правды; храним только то, чего в нём нет.

## 8. Откат при сбое создания кампании

- **Решение:** если после создания кампании упал запрос на поток, удаляем созданную кампанию.
- **Почему:** не оставлять полуготовые кампании в Keitaro.

## 9. Geo — список стран через запятую

- **Решение:** поле принимает одну или несколько стран.
- **Почему:** в макете список, в тексте ТЗ одна страна; список покрывает оба случая.

## 10. Фронт: Jinja2 + Alpine.js, отдаётся из FastAPI

- **Решение:** без React и сборки на Node.
- **Почему:** две формы; весь проект на Python, запуск одной командой.

## 11. SQLite (`aiosqlite`) по умолчанию

- **Решение:** Postgres подключается сменой `DB_URL`.
- **Почему:** простой запуск для проверяющих.

## 12. TDD

- **Решение:** код пишется только через Red → Green → Refactor (правила в AGENTS.md).
- **Почему:** требование к процессу; тесты на моках Keitaro позволяют работать без доступа к инстансу.

## 13. Состояние проекта: git + PLAN.md + DECISIONS.md

*Заменено №14.*

- **Решение:** история — в git, план и открытые вопросы — в `docs/PLAN.md`, решения — здесь.
  Указания для агентов — в `AGENTS.md`, `CLAUDE.md` ссылается на него.
- **Почему:** не дублировать историю git; `AGENTS.md` читают Cursor и Windsurf, `CLAUDE.md` — Claude Code.

## 14. План с галочками; git ведёт только пользователь

*Заменяет №13.*

- **Решение:** `docs/PLAN.md` хранит все шаги с чекбоксами: сделанные `[x]` остаются, текущий помечен.
  Агент читает git (`log`, `status`, `diff`), но не делает коммиты и не пушит.
  Указания для агентов — в `AGENTS.md`, `CLAUDE.md` ссылается на него.
- **Почему:** коммиты делает пользователь, поэтому прогресс должен быть виден в плане, а не только в git;
  `AGENTS.md` читают Cursor и Windsurf, `CLAUDE.md` — Claude Code.

## 15. Редактор хранит состояние потоков и офферов у нас в БД

*Дополняет №7.*

- **Решение:** в БД храним потоки кампании и привязки оффер ↔ поток со статусом
  (active / removed / добавлен в черновике), долей, пином и флагом «есть неопубликованные изменения».
  Keitaro меняется только по Push to KT; Fetch синхронизирует его состояние в нашу БД.
- **Почему:** так работает эталонная обёртка из видео: черновик, Cancel, архив removed-офферов
  с Bring back и пины живут только у нас, в Keitaro их нет.

## 16. Зависимости и окружение через uv

- **Решение:** `pyproject.toml` + `uv.lock`; установка `uv sync`, запуск `uv run ...`. Python ≥ 3.12.
  Dev-зависимости (pytest, pytest-asyncio, respx, ruff) в группе `dev`. Линтер и форматтер — ruff.
- **Почему:** быстрая и воспроизводимая установка по lock-файлу; одна команда для проверяющих.

## 17. Настройки БД отдельно от настроек Keitaro

- **Решение:** `DatabaseSettings` (только `DATABASE_URL`) и `Settings(DatabaseSettings)` с `KEITARO_URL`
  и `KEITARO_ADMIN_TOKEN` (`SecretStr`). Alembic берёт URL из `DatabaseSettings`.
- **Почему:** миграции не должны требовать токен Keitaro; токен не светится в repr и логах.

## 18. Папка миграций — `migrations/`, а не `alembic/`

- **Решение:** `script_location = migrations`, async-шаблон Alembic.
- **Почему:** папка `alembic/` в корне совпадает с именем библиотеки: ruff считает её локальным пакетом,
  а импорт `alembic` может её перехватить.

## 19. Клиент Keitaro: httpx снаружи, ошибки — KeitaroError

- **Решение:** `KeitaroClient(base_url, token, http)` получает готовый `httpx.AsyncClient`.
  Любой ответ 4xx/5xx и сетевой сбой превращаются в `KeitaroError(message, status_code)`;
  `status_code = None`, если ответа не было. Пустое тело ответа — `None`.
  `update_stream_offers` отправляет `PUT /streams/{id}` с полным списком офферов: чего нет в списке, удаляется.
- **Почему:** один `AsyncClient` на приложение (пул соединений, закрывается в lifespan),
  в тестах подменяется через `respx`; сервисы ловят одно исключение вместо httpx-специфики.

## 20. Как создаётся кампания (часть 1)

- **Решение:**
  - Домен, группа и источник ищутся в Keitaro по имени из настроек
    (`KEITARO_DOMAIN`, `KEITARO_GROUP`, `KEITARO_TRAFFIC_SOURCE`); не нашли — `CampaignSetupError` (503).
  - Оффер проверяется до создания кампании; нет в Keitaro — `OfferNotFoundError` (404).
  - Alias: slug имени + 6 случайных символов (`my-campaign-x7k2pq`): трекер общий, alias должен быть уникален.
  - Поток 1: `regular`, позиция 1, `redirect` → `https://google.com`, фильтр `country` accept по списку geo.
  - Поток 2: `default`, позиция 2, `landings`, оффер с долей 100%.
  - Если поток не создался — кампания удаляется (архивируется) в Keitaro; сбой отката логируется,
    но не скрывает исходную ошибку. В реестр БД пишется только полностью созданная кампания.
  - Ошибки Keitaro отдаются фронту как 502 с текстом ошибки.
- **Почему:** так устроены рабочие кампании по этому ТЗ в живом трекере (см. PLAN.md, «Реальный формат
  потоков»); `default` для второго потока точнее всего передаёт «всех остальных — на оффер».

## 21. Тесты API через настоящее приложение

- **Решение:** фикстура `api` создаёт приложение `create_app()` и подменяет через `dependency_overrides`
  настройки, клиент Keitaro (с моком respx) и сессию БД (in-memory). `ASGITransport` respx не перехватывает.
- **Почему:** проверяем весь путь HTTP → сервис → Keitaro/БД, не трогая внешний мир.
