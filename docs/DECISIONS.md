# Принятые решения

Журнал решений: только дописывается. Если решение пересмотрено, добавь новую запись
«Заменяет №N», а старую пометь «Заменено №M», но не удаляй.

Формат записи: номер, заголовок, решение, почему.

## 1. Стек: FastAPI + SQLAlchemy 2.0 (async, ORM) + Alembic

- **Решение:** ORM в стиле 2.0 (`Mapped`, `mapped_column`, `select()`), `AsyncSession`, миграции через Alembic.
- **Почему:** требование вакансии; стиль 1.x (`Column`, `session.query`) устарел.

## 2. Тонкий бэкенд-прокси между фронтом и Keitaro

- **Решение:** фронт ходит только в наше API, бэкенд ходит в Keitaro.
- **Почему:** API-ключ не должен попадать в браузер; CORS; сценарии из нескольких запросов держим на сервере.

## 3. Свой клиент Keitaro на `httpx.AsyncClient`

- **Решение:** не используем сторонние SDK.
- **Почему:** официального Python SDK нет; keitaropy синхронный, aiokeitaro заброшен.

## 4. Слои: `api → services → repositories / clients → db`

- **Решение:** `api/` (роутеры), `services/` (логика), `schemas/` (Pydantic), `models/` (SQLAlchemy),
  `repositories/`, `db/`, `clients/keitaro/`, `core/config.py`.
- **Почему:** аналог Go-структуры handlers/services/domain/repos/db; сервисы не зависят от FastAPI и тестируются отдельно.

## 5. Pydantic-схемы отдельно от ORM-моделей

- **Решение:** `schemas/` и `models/` не смешиваются.
- **Почему:** ORM-объекты завязаны на сессию и ленивые загрузки; DTO и таблицы меняются по разным причинам.

## 6. Модели Keitaro отдельно от наших

- **Решение:** ответы Keitaro описаны в `clients/keitaro/schemas.py`.
- **Почему:** изменения их API не расползаются по нашему коду.

## 7. Что хранится в БД

- **Решение:** реестр созданных кампаний, журнал изменений офферов, кэш справочников.
- **Почему:** Keitaro остаётся источником правды; храним только то, чего в нём нет.

## 8. Откат при сбое создания кампании

- **Решение:** если после создания кампании упал запрос на поток, удаляем созданную кампанию.
- **Почему:** не оставлять полуготовые кампании в Keitaro.

## 9. Geo — список стран через запятую

- **Решение:** поле принимает одну или несколько стран.
- **Почему:** в макете список, в тексте ТЗ одна страна; список покрывает оба случая.

## 10. Фронт: Jinja2 + Alpine.js, отдаётся из FastAPI

*Заменено №22.*

- **Решение:** без React и сборки на Node.
- **Почему:** две формы; весь проект на Python, запуск одной командой.

## 11. SQLite (`aiosqlite`) по умолчанию

- **Решение:** Postgres подключается сменой `DB_URL`.
- **Почему:** простой запуск для проверяющих.

## 12. TDD

- **Решение:** код пишется только через Red → Green → Refactor (правила в AGENTS.md).
- **Почему:** требование к процессу; тесты на моках Keitaro позволяют работать без доступа к инстансу.

## 15. Редактор хранит состояние потоков и офферов у нас в БД

*Дополняет №7.*

- **Решение:** в БД храним потоки кампании и привязки оффер ↔ поток со статусом
  (active / removed / добавлен в черновике), долей, пином и флагом «есть неопубликованные изменения».
  Keitaro меняется только по Push to KT; Fetch синхронизирует его состояние в нашу БД.
- **Почему:** так работает эталонная обёртка из видео: черновик, Cancel, архив removed-офферов
  с Bring back и пины живут только у нас, в Keitaro их нет.

## 16. Зависимости и окружение через uv

- **Решение:** `pyproject.toml` + `uv.lock`; установка `uv sync`, запуск `uv run ...`. Python ≥ 3.12.
  Dev-зависимости (pytest, pytest-asyncio, respx, ruff) в группе `dev`. Линтер и форматтер — ruff.
- **Почему:** быстрая и воспроизводимая установка по lock-файлу; одна команда для проверяющих.

## 17. Настройки БД отдельно от настроек Keitaro

- **Решение:** `DatabaseSettings` (только `DATABASE_URL`) и `Settings(DatabaseSettings)` с `KEITARO_URL`
  и `KEITARO_ADMIN_TOKEN` (`SecretStr`). Alembic берёт URL из `DatabaseSettings`.
- **Почему:** миграции не должны требовать токен Keitaro; токен не светится в repr и логах.

## 18. Папка миграций — `migrations/`, а не `alembic/`

- **Решение:** `script_location = migrations`, async-шаблон Alembic.
- **Почему:** папка `alembic/` в корне совпадает с именем библиотеки: ruff считает её локальным пакетом,
  а импорт `alembic` может её перехватить.

## 19. Клиент Keitaro: httpx снаружи, ошибки — KeitaroError

- **Решение:** `KeitaroClient(base_url, token, http)` получает готовый `httpx.AsyncClient`.
  Любой ответ 4xx/5xx и сетевой сбой превращаются в `KeitaroError(message, status_code)`;
  `status_code = None`, если ответа не было. Пустое тело ответа — `None`.
  `update_stream_offers` отправляет `PUT /streams/{id}` с полным списком офферов: чего нет в списке, удаляется.
- **Почему:** один `AsyncClient` на приложение (пул соединений, закрывается в lifespan),
  в тестах подменяется через `respx`; сервисы ловят одно исключение вместо httpx-специфики.

## 20. Как создаётся кампания (часть 1)

- **Решение:**
  - Домен, группа и источник ищутся в Keitaro по имени из настроек
    (`KEITARO_DOMAIN`, `KEITARO_GROUP`, `KEITARO_TRAFFIC_SOURCE`); не нашли — `CampaignSetupError` (503).
  - Оффер проверяется до создания кампании; нет в Keitaro — `OfferNotFoundError` (404).
  - Alias: slug имени + 6 случайных символов (`my-campaign-x7k2pq`): трекер общий, alias должен быть уникален.
  - Поток 1: `regular`, позиция 1, `redirect` → `https://google.com`, фильтр `country` accept по списку geo.
  - Поток 2: `default`, позиция 2, `landings`, оффер с долей 100%.
  - Если поток не создался — кампания удаляется (архивируется) в Keitaro; сбой отката логируется,
    но не скрывает исходную ошибку. В реестр БД пишется только полностью созданная кампания.
  - Ошибки Keitaro отдаются фронту как 502 с текстом ошибки.
- **Почему:** так устроены рабочие кампании по этому ТЗ в живом трекере (см. PLAN.md, «Реальный формат
  потоков»); `default` для второго потока точнее всего передаёт «всех остальных — на оффер».

## 21. Тесты API через настоящее приложение

- **Решение:** фикстура `api` создаёт приложение `create_app()` и подменяет через `dependency_overrides`
  настройки, клиент Keitaro (с моком respx) и сессию БД (in-memory). `ASGITransport` respx не перехватывает.
- **Почему:** проверяем весь путь HTTP → сервис → Keitaro/БД, не трогая внешний мир.

## 22. Фронт — отдельное React-приложение; сначала бэкенд

*Заменяет №10.*

- **Решение:** бэкенд отдаёт только JSON API (`/api/...`, Swagger на `/docs`), без HTML-шаблонов.
  Фронт — отдельное React-приложение, делается после бэкенда. Для его dev-сервера понадобится CORS
  (разрешённые origin из настроек).
- **Почему:** решение пользователя; API-first позволяет закончить и проверить бэкенд отдельно.

- **Почему:** решение пользователя; так видно, где мы опирались на факты, а где на свою интерпретацию.

## 24. Модель данных редактора

- **Решение:**
  - `streams`: поток Keitaro (`keitaro_id`, `campaign_id` — id кампании в Keitaro, `name`, `position`,
    `type`, `fetched_at`). Кампания не обязана быть создана через нас: редактор работает с любой.
  - `stream_offers`: привязка оффер ↔ поток (уникальна в потоке): `offer_id`, `offer_name`,
    `status` (active/removed), `share`, `pinned`, `sort_order` и опубликованный снимок
    `published_status`, `published_share`.
  - Черновик не хранится флагом, а выводится: привязка изменена, если `status`/`share` отличаются
    от опубликованных или она не публиковалась (`published_status = NULL`); у потока черновик, если
    изменена хоть одна привязка. Cancel = вернуть published_* и удалить непубликованные привязки.
  - Пин — только наша настройка, в Keitaro не уходит и черновиком не считается; ручной ввод доли
    меняет `share` и ставит пин (DISPUTED.md №1).
  - Enum хранится строкой-значением (`'active'`), без нативного ENUM — одинаково в SQLite и Postgres.
- **Почему:** один источник правды для «жёлтого» потока; Cancel и архив removed-офферов
  работают без отдельной таблицы истории.

## 25. Пересчёт долей — чистая функция `rebalance`

- **Решение:** `app/services/shares.py`: `rebalance(slots) -> list[int]`, без БД и Keitaro.
  - removed → 0 (пин у removed не держит долю);
  - активные запиненные сохраняют долю;
  - активные незапиненные делят `100 − сумма пинов` поровну, остаток по 1% сверху списка
    (сверено с видео: 34/33/33, 4 × 25, пин 25 → 38/37/25);
  - нет активных офферов → все 0 (DISPUTED.md №2).
  - `ShareError` (DISPUTED.md №3), если: доля пина вне 0–100; сумма пинов > 100; незапиненным не
    достаётся хотя бы по 1%; все активные запинены, а сумма ≠ 100.
- **Следствие правила №3:** если остались только запиненные офферы с суммой < 100 (например, пин 25%
  и удаляем последний незапиненный), операция отклоняется — сначала нужно снять пин.
- **Почему:** логика долей — ядро «верных цифр» из ТЗ; чистую функцию легко покрыть примерами из видео.

## 26. Сервис редактора `OfferEditor`

- **Решение:** `app/services/offer_editor.py`, потоки адресуются по `keitaro_id`.
  - `fetch(campaign_id)`: синхронизация с Keitaro. Новые потоки создаются, удалённые в Keitaro — удаляются
    у нас; у привязок текущее = опубликованное = Keitaro; пропавший в Keitaro оффер → removed 0%;
    новый в Keitaro → active в конце списка; доли без пересчёта (DISPUTED.md №4, №6).
    Повторный Fetch перезаписывает неопубликованный черновик (DISPUTED.md №8, открыт).
  - `add_offer`, `remove_offer`, `bring_back`, `pin`, `unpin`, `set_share`: меняют только нашу БД
    и пересчитывают доли через `rebalance`; при `ShareError` изменение откатывается.
    Пин сам по себе черновиком не считается; ручная доля закрепляется.
  - `push`: `PUT /streams/{id}` с активными офферами в порядке списка; после успеха published_* = текущее,
    привязки «добавили и удалили до публикации» удаляются. Ошибка Keitaro — черновик сохраняется.
  - `cancel`: непубликованные привязки удаляются, остальным возвращается опубликованное; пины не трогаем.
  - Ошибки: `StreamNotFoundError` (сначала Fetch), `OfferNotFoundError`, `OfferAlreadyInStreamError`
    (в т.ч. removed — подсказка про Bring back), `OfferNotInStreamError`, `ShareError`.
- **Почему:** повторяет поведение эталона из видео; Keitaro трогает только `push` и `fetch`.

## 27. Проверка перед Push: поток не изменён в Keitaro

- **Решение:** перед `PUT /streams/{id}` читаем поток (`GET /streams/{id}`) и сравниваем офферы и доли
  в Keitaro с опубликованным снимком (`published_*` active). Отличаются — `StreamChangedInKeitaroError`
  (в API — 409), ничего не отправляем, черновик сохраняется; пользователю — сделать Fetch.
- **Почему:** Push отправляет полный список офферов и молча затёр бы чужие правки в Keitaro
  (оптимистичная блокировка). Первый уровень идеи «помечать изменения из Keitaro» (DISPUTED.md №8).

## 28. Fetch — трёхстороннее слияние с пометками и конфликтами

- **Решение:**
  - Новые поля `stream_offers`: `keitaro_change` (added / removed / share_changed), `keitaro_share_before`,
    `conflict`. Первая загрузка потока пометок не ставит.
  - Fetch: K = P — ничего; K ≠ P и D = P — принять K с пометкой; K ≠ P и D ≠ P — конфликт (D не трогаем,
    P := K). Доли не пересчитываются.
  - `resolve(offer, keep="mine"|"keitaro")` и `resolve_all`; при любом пересчёте конфликтные офферы
    заморожены; после выбора неподвижны ещё и офферы с пометкой Keitaro (выбранные цифры не уплывают);
    нет черновика — без пересчёта.
  - Push: `ConflictsPendingError` (409), пока есть конфликты — до запросов в Keitaro. Push и Cancel
    снимают пометки и конфликты (Cancel = состояние Keitaro); `acknowledge` снимает только пометки.
- **Почему:** повторный Fetch больше не теряет черновик и не прячет чужие правки; решение по каждому
  офферу отдельно (идея пользователя). Заменяет поведение «Fetch затирает черновик» из №26.
- **Известное ограничение:** после `acknowledge` пометки сняты, и ранее выбранные при разрешении цифры
  перестают быть неподвижными при следующих выборах.

## 29. REST-API редактора: action-эндпоинты по кнопкам, коды ошибок по смыслу

- **Решение:**
  - Поток адресуется своим id в Keitaro (`/api/streams/{keitaro_id}`) — его видит пользователь и фронт.
  - `GET /api/campaigns` — наши кампании (новые сверху). `POST /api/campaigns/{id}/fetch` — Fetch;
    `GET /api/campaigns/{id}/streams` — черновик из нашей БД без запроса в Keitaro.
  - Операции — POST-«действия» по кнопкам из видео: `…/offers` (Add), `…/offers/{offer_id}/remove`,
    `/bring-back`, `/pin`, `/unpin`, `/resolve` (`{"keep": "mine"|"keitaro"}`), `PUT …/share`
    (`{"share": 0..100}`); на поток — `/push`, `/cancel`, `/resolve`, `/acknowledge`.
    Каждая возвращает поток целиком — фронту не нужно пересчитывать доли самому.
  - Коды: 404 — потока/оффера нет (`StreamNotFoundError`, `OfferNotInStreamError`); 409 — действие не
    подходит состоянию (`StateConflictError` и наследники: `OfferStateError`, оффер уже в потоке, нет
    конфликта, конфликты не решены, Keitaro изменился); 400 — невозможные доли (`ShareError`);
    422 — невалидный запрос; 502 — ошибка Keitaro.
  - `OfferStateError` выделен из `OfferNotInStreamError`: «удалить удалённый» — не «нет оффера».
- **Почему:** Remove не удаляет оффер (он остаётся серым), поэтому `DELETE` вводил бы в заблуждение;
  ответ целым потоком держит единственный источник правды о долях на бэкенде; 404/409 позволяют
  фронту различать «перезагрузи» и «так нельзя».

## 30. Push без черновика — пустая операция

- **Решение:** если в потоке нет черновика (`has_draft` ложно), `push` возвращает поток как есть и не делает
  запросов в Keitaro (ни проверки, ни `PUT`). Пометки об изменениях в Keitaro при этом не снимаются —
  публикации не было.
- **Почему:** трекер общий; `PUT` с тем же содержимым — лишняя запись (так и вышло при ручной проверке
  шага 7). Конфликт бывает только при черновике, поэтому блокировка Push по конфликтам не теряется.

## 31. CORS, Docker и README

- **Решение:**
  - CORS: адреса фронта в `CORS_ORIGINS` через запятую, по умолчанию `http://localhost:5173` (Vite).
    Отдельные `WebSettings`: middleware подключается при создании приложения и не должен требовать
    доступа к Keitaro.
  - Docker: один сервис `api` (`python:3.13-slim` + uv, зависимости по `uv.lock`), SQLite в именованном
    томе. Миграции — `alembic upgrade head` перед стартом uvicorn при каждом запуске контейнера.
  - README: быстрый старт в Docker, локальный запуск, команды Alembic, таблица настроек, список API
    и коды ошибок.
- **Почему:** ТЗ требует README по миграциям и запуску; один `docker compose up` без отдельного шага
  миграций — проще всего для проверяющего. Postgres не добавляли: ТЗ его не требует, SQLite достаточно.

## 32. Раскладка репозитория: `backend/` и `frontend/`

- **Решение:** монорепо. Бэкенд (код, тесты, миграции, `pyproject.toml`, Dockerfile, `.env`) — в `backend/`,
  React-приложение — в `frontend/`. В корне — `docker-compose.yml` (поднимает оба сервиса), README,
  AGENTS/CLAUDE и `docs/`. Команды бэкенда (`uv`, `pytest`, `alembic`) запускаются из `backend/`.
- **Почему:** сдаётся одна ссылка на GitHub с одним README и одной командой запуска; две папки
  верхнего уровня читаются проверяющим сразу.

## 33. Стек фронтенда

- **Решение:** Vite + React + TypeScript; логика — в моделях **effector**, запросы — **farfetched**
  (`createQuery` / `createMutation` поверх наших `createEffect`), утилиты — patronum; роутинг —
  React Router (открытие страницы вызывает событие модели); UI — shadcn/ui на Tailwind; типы API
  генерируются из `/openapi.json` (openapi-typescript + openapi-fetch). Структура простая:
  `api/`, `models/`, `pages/`, `components/`. TDD: тест сначала на модель через `fork` + `allSettled`
  (Vitest), эффекты подменяются через `handlers`; компоненты — Testing Library, где поведение в UI.
- **Почему:** пользователь хочет отдельный слой логики на effector; farfetched даёт статусы, ошибки
  и защиту от гонок (автокомплит) без ручного кода; бизнес-логика долей остаётся на бэкенде,
  фронт только показывает поток и вызывает действия. Заменяет TanStack Query из обсуждения.

## 34. Каркас фронтенда

- **Решение:**
  - TypeScript 5.9 вместо 7 из шаблона Vite: генератор типов `openapi-typescript` и остальная экосистема
    пока требуют TS 5 (у нативного TS 7 нет совместимого JS API). `strict` включён явно.
  - Типы API генерируются из `app.openapi()` бэкенда без запуска сервера (`npm run api:types`);
    `src/api/openapi.json` и `schema.d.ts` лежат в репозитории — сборка фронта не зависит от бэкенда.
  - Клиент: openapi-fetch с базой `window.location.origin` (API на том же адресе, что фронт:
    в dev — прокси Vite, позже — nginx). Ошибка API → `ApiError(status, detail)`, сообщение бэкенда
    показывается пользователю как есть.
  - Запросы — `createEffect` в `src/api/*`, поверх них `createQuery`/`createMutation` в `src/models/*`;
    в тестах подменяются эффекты (`fork({ handlers })`). Страница сообщает модели об открытии событием
    (`campaignsPageOpened`), загрузкой управляет модель.
  - Линтер — oxlint из шаблона; сгенерированные компоненты `src/components/ui` не линтим.
  - `.claude/launch.json` — запуск бэкенда и фронта для предпросмотра в Claude Code.
- **Почему:** работающий каркас с первым сквозным сценарием (список кампаний) проверяет всю цепочку:
  типы → клиент → модель → страница → прокси → бэкенд.

## 35. Форма «New campaign» и автокомплит офферов

- **Решение:**
  - Поиск офферов — фабрика `createOfferSearch()` (та же модель будет у Add в редакторе): запрос после
    паузы ввода 300 мс (`debounce` из patronum), `concurrency: TAKE_LATEST` — опоздавший ответ на старый
    текст отбрасывается; выбранный оффер сбрасывается, как только снова начинают печатать.
  - Форма на главной над списком. Отправить можно, когда заполнены название, гео и выбран оффер;
    формат гео не дублируем на фронте — проверяет бэкенд. 422 раскладывается по полям
    (`ApiError.fields`, сообщение у поля), прочие ошибки — общим сообщением. После создания: ссылка на
    кампанию и в редактор, форма очищается, список кампаний перезагружается.
  - Автокомплит — свой небольшой компонент с ролями ARIA combobox/listbox/option, а не Combobox shadcn:
    логика целиком в модели, компонент только рисует; проще тестировать через роли.
  - У карточки формы `overflow-visible`: у `Card` из shadcn `overflow-hidden` обрезал выпадающий список.
- **Почему:** валидация гео уже есть на бэкенде с понятными сообщениями — дублирование разошлось бы;
  гонка ответов автокомплита — реальный баг при быстром вводе (воспроизведён тестом).

## 36. Фронт редактора

- **Решение:**
  - Все кнопки над потоком — одно событие `actionRequested(StreamAction)` (размеченный союз `kind`:
    add, remove, bringBack, pin, unpin, share, resolve, resolveAll, acknowledge, push, cancel) и одна
    мутация; `runStreamAction` превращает действие в HTTP-запрос. Ответ — поток целиком, он заменяет
    свой поток в `$streams`; доли и черновик фронт не считает.
  - Пока у потока идёт запрос, поток заблокирован (`$busyStreams`, кнопки неактивны, новые действия
    над ним не отправляются): ответы — поток целиком, параллельные запросы могли бы затереть друг друга.
  - Одна ошибка над потоками (`$editorError`) с текстом бэкенда, закрывается кнопкой или новым действием.
  - Add: поле поиска открыто под одним потоком за раз, модель `createOfferSearch` общая.
  - Ручная доля: клик по проценту → числовое поле (значение выделено, Enter — сохранить, Escape и потеря
    фокуса — отмена); число вне 0–100 не отправляется, поле остаётся с подсказкой.
  - Черновик — жёлтая карточка с меткой «Черновик»; при конфликтах Push неактивен, на оффере — обе
    версии и кнопки «Моё» / «Keitaro», на потоке — «Всё моё» / «Всё из Keitaro» и «Понятно» для пометок.
  - Открытие другой кампании сбрасывает потоки прошлой, пока грузятся новые.
  - Не сделано из видео: View in KT, Show all offers, Stats/Trends (статистика — опциональный шаг 12).
- **Почему:** один путь для всех действий — одна точка для блокировки, ошибок и обновления; поведение
  повторяет видео и решения бэкенда (№26–30).
