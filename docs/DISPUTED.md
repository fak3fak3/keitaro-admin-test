# Спорные вопросы

Вопросы, на которые нет прямого ответа ни в ТЗ, ни в видео, ни в документации API.
Ответ — наша интерпретация, поэтому её нужно уметь объяснить проверяющим.

Формат: вопрос, что известно, варианты, статус. Статусы:
- **открыт** — решения нет, не реализовывать до ответа;
- **предложение** — есть вариант, ждёт подтверждения пользователя;
- **решён** — выбран вариант (кто и когда решил). Важное решение дублируется в DECISIONS.md.

Источники: ТЗ (раздел «Задача» в PLAN.md), видео (раздел «Поведение редактора» в PLAN.md),
спецификация API ([keitaro-openapi.yaml](keitaro-openapi.yaml)).

## 1. Ручной ввод доли и пин

**Статус:** решён (пользователь, 2026-11-20).

**Решение:** доля оффера считается автоматически, пока пользователь её не задал. Можно:
- **запинить** текущую долю: она перестаёт пересчитываться;
- **задать число вручную** (0–100): введённая доля тоже закрепляется, как пин, иначе следующий
  пересчёт её затрёт;
- снять пин: доля снова считается автоматически.

Незакреплённые активные офферы делят остаток `100 − сумма закреплённых` поровну. Ограничения те же,
что в вопросе 3: нельзя закрепить так, чтобы незакреплённым не осталось доли или остаток некому отдать.

**Что известно:**
- Видео: процент в колонке Share — кликабельная ссылка, рядом иконка пина. Что делает клик по %, не показано.
  Пин показан: запиненная доля не меняется при add/remove/bring back.
- API: у оффера в потоке есть `share` (integer, «Percentage of Traffic Sent to This Offer») и `state`.
  Любую долю задать можно. Понятия «пин» в Keitaro нет: пин существует только в нашей обёртке.
- **Проверено на живом Keitaro (2026-11-20, своя кампания `test_mirolyubov_campaign1`, поток 1333643):**
  - сумма долей ≠ 100% **принимается**: доля 50% и даже 0% у единственного оффера сохраняются (200);
  - доля одного оффера ограничена 0–100: на 150 ответ 422 `{"share": ["Share must be no more than 100"]}`;
  - один и тот же оффер дважды (60 + 60) Keitaro схлопывает в одну запись (60%), поэтому сумму > 100
    на разных офферах проверить не удалось: по ключу доступен только один оффер.
  - Вывод: следить, чтобы сумма была 100%, должна наша обёртка, Keitaro этого не гарантирует.

**Варианты:**
- а) Ручного ввода нет, только автоматический пересчёт и пин текущей доли.
- б) Клик по % открывает ввод; введённая доля сразу пинится (иначе следующий пересчёт её перезапишет).

## 2. Удаление последнего активного оффера

**Статус:** решён (пользователь, 2026-11-20).

**Решение:** разрешать, как позволяет API. Поток без активных офферов остаётся (removed-офферы видны
в архиве с Bring back); правило «сумма активных = 100%» к пустому потоку не применяется.

**Что известно:**
- Видео: не показано.
- API: спецификация не говорит, допустим ли поток `schema=landings` без офферов.
- **Проверено на живом Keitaro (2026-11-20, поток 1333643):** `PUT /streams/{id}` с `"offers": []` → 200,
  поток остаётся `active` с пустым списком офферов. То есть Keitaro такое **разрешает**.
- Что получает посетитель в таком потоке, проверить не удалось: домен `kylovoa.com` не резолвится в DNS.
  Скорее всего, ничего полезного (оффера нет), но это не проверено.

**Варианты:**
- а) Запрещать удаление последнего активного оффера.
- б) Разрешать; поток без офферов остаётся как есть.

## 3. Пины, которые не оставляют места остальным

**Статус:** решён (пользователь, 2026-11-20; пересмотрен 2026-11-21).

**Что известно:** в видео не показано.

**Решение (пересмотрено пользователем 2026-11-21):** сумма долей ≠ 100% — не запрет, а постоянное
предупреждение на потоке, как в Keitaro; Push разрешён (пример пользователя: единственный оффер с долей
20%). Незакреплённые получают остаток `100 − сумма пинов`, но не меньше 0%. Ошибка — только доля одного
оффера вне 0–100 (её не примет Keitaro, 422).

## 4. Доли после удаления оффера в самом Keitaro

**Статус:** решён (пользователь, 2026-11-20).

**Что известно:** в видео после Fetch оставшиеся офферы показывают доли из Keitaro как есть
(25% + 25%, сумма 50%), пропавший оффер — removed с 0%.

**Решение:** как в эталоне: при Fetch доли берём из Keitaro без пересчёта; пересчёт — при следующем
действии в редакторе (add, remove, bring back, pin).

## 8. Повторный Fetch при неопубликованном черновике

**Статус:** решён (пользователь, 2026-11-20): вариант г — трёхстороннее слияние, уровни 1 и 2.
Уровень 3 (журнал событий) — опционально, в конце.

**Как работает уровень 2:**
- P — опубликованное/последнее виденное в Keitaro (`published_*`), D — черновик, K — Keitaro сейчас.
- Fetch по каждому офферу: K = P — ничего; K ≠ P и D = P — принимаем K с пометкой
  «изменено в Keitaro» (было → стало); K ≠ P и D ≠ P — **конфликт**: черновик не трогаем, P := K.
  Новый в Keitaro — добавлен с пометкой; пропал из Keitaro — removed (или конфликт, если мы его меняли).
  Доли при Fetch не пересчитываются.
- Конфликт решается **на каждом оффере**: «оставить моё» (D) или «взять из Keitaro» (P); на потоке —
  массовые «всё моё» / «всё из Keitaro» как сокращение.
- Пока оффер в конфликте, при любом пересчёте он заморожен (как запиненный), чтобы не менялась цифра,
  по которой решение ещё не принято.
- После выбора доли пересчитываются так, чтобы выбранные цифры не «уплыли»: неподвижны пины,
  нерешённые конфликты и все офферы с пометкой «изменено в Keitaro»; остаток поглощают только наши
  расчётные доли. Не сходится — оставляем ровно как выбрано. Нет черновика — не пересчитываем вообще:
  выбрав везде «из Keitaro», получаем ровно состояние Keitaro.
  (Уточнено при реализации: «пересчитывать после каждого выбора» приводило к тому, что выбранная
  минутой раньше цифра пересчитывалась при следующем выборе.)
- Push заблокирован, пока есть конфликты. Push и Cancel снимают пометки «изменено в Keitaro»;
  их можно снять и кнопкой «понятно».

**Что известно:** в видео Fetch показан только для опубликованного потока. Что делать, если у потока
есть черновик (добавили/удалили офферы, но не нажали Push), не показано.

**Сейчас (2026-11-20):** Fetch перезаписывает черновик состоянием Keitaro — так получилось из логики
синхронизации, отдельно это не выбиралось.

**Варианты:**
- а) Fetch = «обновить из Keitaro», черновик теряется (текущее поведение).
- б) Fetch отказывает, пока у потока есть черновик: сначала Push или Cancel.
- в) Fetch обновляет только опубликованный снимок, черновик сохраняется поверх.
- г) (идея пользователя, 2026-11-20) трёхстороннее слияние: P — опубликованное/виденное, D — черновик,
  K — Keitaro сейчас. Изменения только в Keitaro принимаем и помечаем («изменено в Keitaro: 25 → 40»),
  изменения с обеих сторон — конфликт с выбором «оставить моё» / «взять из Keitaro», Push заблокирован
  до разрешения. Уровни: 1) проверка перед Push; 2) слияние с пометками и конфликтами; 3) журнал событий.

**Сделано:** уровень 1 — проверка перед Push (DECISIONS.md №27), уровень 2 — слияние (№28).

## 9. Откуда берётся список кампаний и какие кампании можно открыть в редакторе

**Статус:** решён (пользователь, 2026-11-21).

**Решение:** вариант в — список хранит подключённые у нас кампании; на странице можно подключить
существующую кампанию Keitaro по ID. После подключения она попадает в локальный список и открывается
в редакторе. Повторное подключение того же ID идемпотентно. Кампании автоматически из Keitaro не
импортируются, чужие записи не отображаются без явного ввода ID.

**Что известно:**
- ТЗ, часть 2: «Написать редактор **существующей** кампании… добавлять/удалять офферы в кампании».
  Как выбирается кампания и нужен ли список, не сказано. Примерный интерфейс в ТЗ — только форма
  New campaign (Name, Geo, Offer, Create), списка кампаний на нём нет.
- Видео: весь ролик — одна страница обёртки заказчика
  `127.0.0.1:8001/fb/campaigns/<uuid>/streams/`, хлебные крошки «Campaigns / campaign 2 / Keitaro
  Streams», меню AdRobot: Creatives, Bundles, Campaigns, Adsets, Automation, Tasks, Offer groups,
  Offers, Profiles & Accounts. Значит, «кампания» у заказчика — **своя сущность** (UUID, раздел `/fb/`
  — по-видимому, кампании Facebook), привязанная к кампании Keitaro (кнопка View in KT), а редактор —
  её подстраница «Keitaro Streams». Список Campaigns в видео не открывается — это их собственный
  список, не список Keitaro.
- Keitaro (GET /campaigns, 2026-11-21): 408 кампаний (390 active, 18 disabled, удалённые не отдаются),
  225 из них в общей группе FORTESTS; кампании других кандидатов — с префиксами test_ivanov_,
  test_khristoforov_ и т.д. Наших — две (217109, 217519), обе уже в нашем списке.

**Сейчас:** список — наши кампании из БД (созданные через форму), из списка — переход в редактор
`/campaigns/{keitaro_id}`; любую кампанию Keitaro можно открыть, только набрав адрес руками.
Это совпадает с моделью заказчика: своя сущность + подстраница потоков.

**Варианты:**
- а) Оставить как есть (модель из видео): список — только наши кампании.
- б) Список из Keitaro (`GET /campaigns`) с фильтром по префиксу имени `test_mirolyubov_`
  (настройка): видны и созданные руками в админке; список не устаревает. Чужие кампании не видны.
- в) (а) + «Подключить существующую кампанию Keitaro» по id: кампания добавляется в наш список
  (как привязка кампании к Keitaro у заказчика), дальше — редактор. Чужие — только сознательным
  вводом id.

**Выбрано пользователем:** (в) — повторяет модель заказчика (своя кампания, привязанная к Keitaro) и закрывает
«существующую кампанию», созданную не через нас; (б) на общем инстансе даёт тот же результат, что
сейчас, но зависит от соглашения об именах.
